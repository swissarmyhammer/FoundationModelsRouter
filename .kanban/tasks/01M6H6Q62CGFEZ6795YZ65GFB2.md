title: Send the live toolCall and running toolStatus events when the call starts, not at the end of the submission

## What
The write-ahead card (01M6GK7RHHHC6B6QMJ25FT1QDT) records a `.toolCallStarted` marker when a tool call starts. The live `toolCall` and running `toolStatus` events still go out at the END of the submission (`emitSessionEvents` in `Session/RoutedSessionActorRecording.swift`). A host that shows progress sees a call only after it ended.

An early version of this change failed 4 existing tests: `SessionObserverSeedingTests` (grouped rows) and `ToolInvocationLivenessTests` (event order). Cause: `SessionObserver` closes the narration text of a pass only when the open text row is the last row. An early call row stops the narration from joining its call group.

## Do (design first, in a task comment)
1. Change `SessionObserver` so an early call row does not break the grouping of narration text with its calls (group by pass, not by row order).
2. Emit `toolCall` and a running `toolStatus` from the started-marker path (`RoutedSessionActor.deliver(invocation:)`), once per call id. The end-of-submission diff skips the ids already emitted (keep a set of started ids).
3. Update the tests that assert the event order, with a reason for each change.

## Acceptance Criteria
- [ ] A host sees `toolCall` and running `toolStatus` when the call starts.
- [ ] No call is announced twice.
- [ ] The observer rows group the same as before for a clean run.

## Tests
- [ ] Extend `ToolInvocationLivenessTests` and `SessionObserverSeedingTests`. Run the full `swift test`.

- [x] `Sources/FoundationModelsRouter/Session/RoutedSessionActorRecording.swift:518` `duplication/duplication` — The two-event announcement of a starting tool call is written twice in this change: a `toolCall` followed by a running `toolStatus`. `announceStart(of:)` sends it through `deliverPost`, and `emitSessionEvents` sends it through `onEvent` when the call was not announced earlier. The two copies must agree on the event shape and the status. A change to one, such as a new field or a different status, can leave the other behind, so the live stream would then show a call one way when it starts and another way when the diff records it. Extract one helper that takes the call's id, name and arguments text and a sink closure, and emits the pair. Call it from both sites, and pass `deliverPost` or `onEvent` as the sink. Keep the argument-text source as the one parameter that differs, and check that both sites produce the same text for the same call before merging them.
- [x] `Sources/FoundationModelsRouter/Session/RoutedSessionActorRecording.swift:518` `reuse/reuse` — announceStart rebuilds the same toolCall plus running toolStatus pair that emitSessionEvents already builds for a call. Two copies of this pair can drift apart, for example if one later adds a field or changes the status. The only difference is the sink: emitSessionEvents uses onEvent and announceStart uses deliverPost. Extract one helper that takes the call and a sink, for example `Self.announcedCallEvents(for call: Transcript.ToolCall) -> [SessionEvent]`, and have both paths emit its result: `for event in Self.announcedCallEvents(for: call) { onEvent(event) }` in emitSessionEvents, and `deliverPost` for each event in announceStart. Then the pair is defined in one place.
- [x] `Tests/FoundationModelsRouterTests/ToolInvocationLivenessTests.swift:312` `test-integrity/no-test-cheating` — The arguments check compares the announced toolCall's argumentsJSON to the argumentsJSON taken from the same announced event, so it can never fail on the arguments. The test therefore does not prove the call's arguments are announced correctly. This is a trivial assertion on the arguments field of a new test. Replace the self-derived value with the expected arguments JSON for the scripted call, for example the JSON that `.literal(ScriptedToolFixture.firstStepName)` produces. - [x] `Sources/FoundationModelsRouter/Session/RoutedSessionActorRecording.swift:516` `correctness/live-announcement-never-settles` — `announceStart(of:)` sends `toolCall` and a running `toolStatus` through `deliverPost`, and it inserts the id in `announcedToolCallIDs`. The id leaves the set, and the host gets a `completed` or `failed` toolStatus, only in `emitSessionEvents` of a diff that has an event sink (`onEvent`) and that includes the `.toolCalls` entry of the call. A call whose attempt is rolled back before the diff records its entry, or a submission with a nil `onEvent`, never reaches that path. The host keeps a running row that never settles, and the id stays in the set for the life of the session. Before this change those cases sent no live event, so the stuck row is new. Make the announcement settle on every path: when a submission ends (the diff, a failure, a rollback, or a cancel), send a `failed` toolStatus for each id that is still in `announcedToolCallIDs` and remove it, whether or not `onEvent` is non-nil. Add a test for a rolled-back attempt and a test for a nil sink.
