    ### Research and design (implement)
    - Run plane order (FoundationModelsExtras RunPlaneActor): `complete(elicitationId:)` returns at once and posts the completion in a new task. The run gets the accept only after `post(elicitationCompleted:)` returns. A run-plane end (cancel, sweep, endElicitation) gives the run its answer only after `post(elicitationEnded:response:)` returns. `awaitAnswer` makes the question pending before `posting` runs. Thus the count of ElicitationPostings always goes up BEFORE the task that asks ends.
    - Deviation from the named form, with the reason: `RecordedWaitResult.wait(for:endingOnEndOf:)` runs the wait in a task of its own and, after the failure event, reads only `waited.value`. At the completion sites the asking task ends right after the count goes up. The observer of the end can record before the wait task records its result. The test then fails in a run that the program passes (a race). So the new members use `RecordedWaitResult.recordingEnd(of:reportingTo: changes)` with `changes.wait(until:endingOn:)`. That form reads the count again after the end, so the order "count, then end" always passes. Both forms are existing test helpers. No production change.
    - Helper: one private `wait(untilAtLeast:of:endingOnEndOf:sourceLocation:)`, and three members `waitForPosts(_:endingOnEndOf:)`, `waitForCompletions(_:endingOnEndOf:)`, `waitForArrivedEnds(_:endingOnEndOf:)`. The old `waitForPosts(_:)` and `waitForArrivedEnds(_:)` had no caller left, so they are removed. `waitForCompletions(_:)` stays for the three sites below.

The `try #require(completed == .completed)` before two of these does not cover a run plane that resumes the run with no completion post, so those sites also use the new member.
