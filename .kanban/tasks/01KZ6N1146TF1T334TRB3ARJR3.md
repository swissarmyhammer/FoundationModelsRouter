## What
New `Sources/FoundationModelsRouter/Hosting/ToolContext.swift`:

```swift
struct ToolContext: Sendable {
    @TaskLocal static var current: ToolContext?
    // session-scoped: mailbox, upstream sink, session identity, cancellation
    // per-run: completionToken (minted by the invoker at each binding)
}
```

Capabilities on the context (the invoker mints the run's `completionToken` into each binding; session scope for the object, run scope for the correlation):
- `post(_ event:)` and `progress(_ detail:)` — build the `OperationEvent` with this run's `correlationID`/`op`/`tool` pre-filled and forward to the sink. A `nil` `ToolContext.current` at a call site is a safe no-op (the capture-at-start rule: detached tasks don't inherit task locals — the runtime now enforces what `EventEmittingContext`'s doc only requested; keep that rule's text in the doc comment).
- Event field sourcing for a plain wrapped `any Tool` (phase-1 rule; `OperationEvent.tool` and `.op` are non-optional and the journal's `renderedLine(for:)` consumes both): the binder stamps `tool` with the wrapped tool's `name` (the session-visible tool identity) and `op` with `tool.name` as well, until noun/verb registration lands in phase 2 and supplies the canonical `"verb noun"` string. Both stamped into the context at bind time, never left empty.
- `elicit(_ request: ElicitationRequest) async throws -> ElicitationResponse` — park as a pending promise: register a continuation in the `SessionMailbox` keyed by the request's `elicitationId`, post the request upstream as an elicitation-kind event on the run's correlation, suspend until the mailbox resumes it. An elicitation is just another elevation; there is no second machinery. One run can hold several pending elicitations at once.
- The run's `completionToken`, session identity, and cancellation.

No new tool protocol: the registry keeps `any Tool`; a conformer reads `ToolContext.current` when it wants capabilities and ignores it otherwise.

## Acceptance Criteria
- [ ] A tool body reading `ToolContext.current` inside `ToolContext.$current.withValue(ctx) { ... }` sees the bound context; a detached `Task {}` inside it sees `nil`; posting through `nil` is a no-op that neither throws nor crashes
- [ ] `post`/`progress` events carry the bound run's `correlationID` without the tool supplying it; a synthesized event for a plain `Tool` carries non-empty `tool` and `op` per the phase-1 stamping rule
