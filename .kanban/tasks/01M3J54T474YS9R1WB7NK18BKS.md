## What
Found in task 01M3HXT453GXVBZPZFXXTZGP9Y (^xtzgp9y). One run of `PooledResidencyTests/droppingLastHandleFreesBudgetForNextResolve` on FoundationModelsExtras f4bd503 did not end (about 1 run in 22). `sample` of the test process showed two threads that wait on `__ulock_wait2`:
- Thread 1 (main): `Router.deinit` -> `PromptCacheSizing.deinit` (`footprintsTask.cancel()`) -> the `onTermination` closure of `ModelPool.footprints` (`ModelPool.swift:88`, `state.withLock { $0.streams[id] = nil }`) -> waits for the pool lock.
- Thread 2: the eviction job `ModelPool.evictIfIdle` -> `state.withLock { $0.publish() }` -> `State.publish()` (`continuation.yield` under the pool lock) -> waits for a different lock.

Probable cause (not proved): `Task.cancel()` runs the cancellation handler of the stream iterator while the runtime holds the status lock of the task. The handler calls `onTermination`, which takes the pool lock. At the same time `publish()` holds the pool lock and `yield` resumes the waiting `next()` of the same task, which needs the status lock of the task. Thus each thread holds the lock that the other thread needs.

The code of `publish()` and `onTermination` is the same at ea9dc99, so the hang can occur there too. 25 runs of the test and 10 parallel runs of the pool suites on ea9dc99 did not show it.

## Fix direction (Extras)
Do not call `continuation.yield` while the pool lock is held, or do not take the pool lock in `onTermination` (for example, remove the stream from the dictionary on the next `publish` when `yield` returns `.terminated`).

## Acceptance Criteria
- [ ] A test in Extras that cancels a `footprints` reader while the pool publishes, repeated many times, never hangs.
- [ ] The router takes the fix with `swift package update FoundationModelsExtras`.
