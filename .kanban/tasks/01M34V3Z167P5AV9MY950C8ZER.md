## Decision (from the owner, 2026-09-22)

`ToolMount.defaultTimeoutSeconds` (120 s, `Hosting/ToolMount.swift:16`) is an invented default and must go. A tool has a timeout only when the host's mount or the tool's own declaration states one. With none stated, the timeout watcher never starts.

## Why

- 120 came with the first run-plane engine (6cffe80, 2026-08-04) with no reason.
- The timeout mechanism stays as the owner's contract keeps it: it bounds the work, progress resets it, a pending elicitation suspends it, expiry reports an error to the model. Only the unstated case changes: from "two minutes" to "none".
- `nil` already means "the watcher never starts" (0c32e22).

## Sites

- `ToolMount.swift:15-20`: the constant and the `.synchronous` mount, which passes it. `:36`: `init(mode:timeout: = Self.defaultTimeoutSeconds)`.
- Every reference to `defaultTimeoutSeconds` in `Sources`, `Tests`, `IntegrationTests`, `Examples` (search it).
- Tests that assert an unconfigured tool times out at 120 s. Replace with: an unconfigured tool that runs 3 s with no progress completes; a mount with `timeout: 1` times out.

## Do this

1. Delete the constant. `.synchronous` is `ToolMount(mode: .runToCompletion, timeout: nil)`. `init(mode:timeout:)` defaults `timeout` to `nil`.
2. Rewrite the docs that name 120 s or "the stock per-call timeout".
3. Update the tests as above.
4. Do not add a default anywhere else. A tool's own `BackgroundTool.mount` and `timeout(from:)` stay as they are.

## Acceptance
