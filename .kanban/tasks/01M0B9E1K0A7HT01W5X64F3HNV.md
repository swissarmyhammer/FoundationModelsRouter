title: The pending-runs rendering can defeat the fold on its own — the retention bound never measures it

Found while `^azd033m` corrected the `summaryRetentionRatio` doc comment. The doc gap is corrected there. This card is the behaviour, which that card was told to leave alone.

## The problem

`Summarization.cut(_:toCharacters:)` bounds the summary TEXT. `Compactor`'s did-not-shrink guard measures the whole replacement ENTRY.

`CompactionSegment.boundaryEntry(id:summaryText:content:)` puts a second `.text` segment on that entry when the session has parked runs. The segment holds `CompactionSegment.renderedPendingRuns(_:)`. `SegmentPayload.contentByteCount` counts a `.text` segment in full, so the guard sees those bytes. The cut never bounded them.

Unlike the `User: `/`Assistant: ` labels, this cost does not scale with the span. The code charges it per parked run.

## The measurement

Measured with a byte-identical copy of `renderedPendingRuns(_:)` and a 26-character ULID completion token.

| parked runs | op | progress | bytes |
|---|---|---|---|
| 1 | `run tool` | none | 217 |
| 3 | `run tool` | none | 385 |
| 5 | `run tool` | none | 553 |
| 6 | `run tool` | none | 637 |
| 10 | `run tool` | none | 973 |
| 10 | `generate completion` | 40 characters | 1413 |

The heading is 134 bytes. One run line is 20 bytes of framing, plus the 26-character token, plus the op, plus 29 bytes when no progress was reported (or 22 bytes plus the detail when one was). Each further run adds that line and one line break.

The cut's byte bound is `retained * Compactor.charsPerTokenEstimate`. The `minimumSummaryTokens` floor gives 512 bytes. The `maximumSummaryTokens` cap gives 2000 bytes.

- Six parked runs come to 637 bytes. That is more than the whole 512-byte floor bound.
- Ten parked runs come to 973 bytes. That is 49% of the 2000-byte cap bound.

## Why this is a defect and not only a doc gap

`summaryRetentionRatio` is `0.8`, so the margin is about a fifth of the rendered content. The pending-runs rendering stays inside that margin only while its bytes are less than a fifth of the span bytes.

- One parked run needs a span above about 1085 bytes.
- Ten parked runs need a span above about 4865 bytes.

Below the `minimumSummaryTokens` floor the bound is a flat 512 bytes. Six parked runs exceed that bound on their own. No summary, however short, can then make the fold shrink the transcript.

The result is bounded. `Compactor` discards the fold and returns the original transcript. That is the safe failure. But a session that parks background runs and then folds a modest span cannot compact at all, and that is the case the pending-runs feature exists for.

## What to do

1. Reproduce it first. Write a test that folds a small span with several parked runs and shows the fold discarded. Prove the pending-runs rendering is the cause: the same fold with no parked runs must be applied.
2. Then decide the fix. Do NOT change `summaryRetentionRatio` to hide the symptom. Options to weigh, each measured, not argued:
   - Subtract the pending-runs rendering from the bound the cut applies, so the cut bounds the whole replacement entry rather than the summary text alone.
   - Bound the pending-runs rendering itself, the way `ToolOutputCapping` bounds tool output.
   - Leave the boundary entry alone and state the requirement, if the measurement shows the case cannot arise.
3. Whatever is chosen, keep the four properties `^azd033m` protected: `Compactor` untouched, the empty-summary refusal before any cut, `outputTokenCeiling(forSummaryAllowance:)` and `reasoningTokenHeadroom` untouched, and no cut that can return an empty summary from a non-empty answer.
