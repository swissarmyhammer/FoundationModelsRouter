title: Stable source-derived identity for SessionProjection entries
---
## Problem

`SessionProjection.TranscriptEntry.id` gets a fresh `ULID.generate()` value each time an entry is made (Sources/FoundationModelsRouter/Session/SessionProjection.swift:108). The id does not come from the source data. Two projections of the same session thus give different ids for the same content. SwiftUI `ForEach` uses these ids. When the app builds the projection again — after a restore, a re-seed, or in a second window — all ids change. The UI loses scroll position, replays animations, and resets row state. A stable UI is not possible.

A second problem: a projection row has no join key back to the raw `Transcript.Entry` or the recording. A UI cannot navigate from a row to the recorded entry.

## Proposed solution

Derive each row's identity from the source data:

- **Tool-call rows**: use the SDK `Transcript.ToolCall.id`. `SessionEvent.toolCall(id:name:argumentsJSON:)` already carries it.
- **Text and reasoning rows**: the SDK entry id is not known while deltas stream. Give the row a provisional id. Adopt the SDK `.response` / `.reasoning` entry id when the turn's snapshot diff makes it known. To do this, add entry-id data to the `SessionEvent` vocabulary (for example, a case that closes an entry with its SDK id). Do not break current consumers.
- **Compaction rows**: `CompactionResult` has no id today. Add one, or key the row on the synthesized summary entry's id.

Also add `sourceEntryId: String?` to `TranscriptEntry`, so a UI can join a row back to the raw transcript and the recording.

## Acceptance

- Two projections built from the same recorded turn sequence must produce equal row ids.
- A seed-then-continue-live flow must keep each row's id stable when the SDK id becomes known, or must document the one adopt-id transition and its UI effect.
- Tests must cover the tool-call id path, the delta-then-adopt path, and the compaction path. #projection
