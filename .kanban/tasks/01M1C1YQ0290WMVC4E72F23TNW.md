## What

`ToolContext.mount(_:op:as:postingTo:)` (card ^bbbkas1) has a documentation comment
that is false in a way a reader cannot detect. Two corrections, both measured by the
consumer against `d576a72`.

### 1. The sink does not carry a swept terminal

The comment says the caller's sink observes every event the run produces. It does not.
`close()` sweeps a background run through the MAILBOX, and a mailbox-originated
terminal never passes through the mount's sink at all.

Measured, one background shell run, after `close()`:

```
run's own token = 01M1C1R4H4VWK7MJTKYVP322JQ
mounting run    = 01M1C1R4H3G4WSP07XB1EG5V2H

caller sink : kinds=[.progress]   correlations=[01M1C1R4H4VWK7MJTKYVP322JQ]
journal     : kinds=[.completed]  correlations=[01M1C1R4H4VWK7MJTKYVP322JQ]
```

The `.progress` event reached the sink on the run's own token, so `postingTo:` works
and survives backgrounding. The terminal went only to the journal.

The behaviour is probably correct: a mailbox-originated event is not the run posting
something of its own. This card does not change it. It makes the comment say what is
true — the sink carries what the RUN posts, and a swept terminal is read from the
journal.

### 2. The journal's correlation depends on which overload mounted the run

Neither the consumer nor this package predicted this, and it is a real consequence of
`postingTo:`:

| mounted with | journal shows |
|---|---|
| `mount(_:op:as:)` | the MOUNTING run's token — `MountedRunUpstreamSink` re-stamps |
| `mount(_:op:as:postingTo:)` | the run's OWN token — no re-stamping layer in the path |

So the same journal read gives a different correlation depending on a choice made at
the mount site. That is defensible, and it is invisible. Say it in both doc comments.

**Correction found while implementing.** The table above holds for what the run POSTS.
It does not hold for a swept terminal. `sweep()` stamps the synthesized terminal from
what `mailbox.track(...)` registered, which is the mounted run's own tool, op, and
completion token — under BOTH overloads. So under the default overload one mounted
background run can stand in the journal under two correlations. Both doc comments now
say this.

## What to do

`Sources/FoundationModelsRouter/Hosting/ToolContext.swift`. No behaviour changes and
