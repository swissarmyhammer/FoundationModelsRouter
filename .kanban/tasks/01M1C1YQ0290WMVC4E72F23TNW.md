    **What the sink carries.** `ToolRun` builds a `RunEventFunnel(upstream: sink, ...)` and gives the run a `ToolContext` whose sink IS that funnel. So every event the run posts — `post(_:)`, `progress(_:)`, `elicit(_:)` — reaches `sink` stamped with the run's own `tool`, `op`, and `completionToken`. A run that ends on its own also reaches `sink`: `ToolRun.settle(arguments:)` builds the terminal and calls `funnel.settleRun(with:)`, which forwards it upstream.

    **What the sink does not carry.** `close()` calls `mailbox.sweep()`. For a run still tracked, `sweep()` runs the run's canceler and, when no natural terminal has been retained, SYNTHESIZES a terminal itself: `OperationEvent(tool: run.tool, op: run.op, correlationID: token, kind: .completed, detail: run.latestProgressDetail ?? It never passes the funnel, so it never reaches `sink`. `close()` then writes it with `outbox.journalWithoutStaging(event:)` — straight to the session journal.

    **Correction to the card's table.** The card says the journal's correlation depends only on the overload. That is true for what the RUN posts, but not for the swept terminal:

    | | what the run posts | a swept terminal |
    |---|---|---|
    | `mount(_:op:as:)` | journal keeps the MOUNTING run's token (`MountedRunUpstreamSink` -> `post(_:)` re-stamps) | journal keeps the mounted run's OWN token |
    | `mount(_:op:as:postingTo:)` | goes to `sink` only, on the run's own token; it reaches the journal only if `sink` itself forwards there | journal keeps the run's OWN token |

    The swept terminal is the same under both overloads, because `sweep()` reads what `mailbox.track(...)` registered, and `BackgroundToolRunner.launch(arguments:)` registers the mounted run's own tool, op, and completion token. The `.progress` event reached the sink on the run's own token, so `postingTo:` works

something of its own. This card does not change it. It makes the comment say what is

### 2. The journal's correlation depends on which overload mounted the run

Neither the consumer nor this package predicted this, and it is a real consequence of
`postingTo:`:

| mounted with | journal shows |
|---|---|
| `mount(_:op:as:)` | the MOUNTING run's token — `MountedRunUpstreamSink` re-stamps |
| `mount(_:op:as:postingTo:)` | the run's OWN token — no re-stamping layer in the path |

So the same journal read gives a different correlation depending on a choice made at
the mount site. That is defensible, and it is invisible. Say it in both doc comments.
