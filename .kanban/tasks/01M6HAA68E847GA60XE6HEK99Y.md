title: PostToolUse gets the final result of the call (OperationResult), not a Bool
---
## What
User request, relayed by the ACP agent session (2026-11-03): the Router sends the final tool result to the PostToolUse hook instead of a Bool. The user allowed the change. NO CODE until the user says so (the other sessions' order: Extras first, then Multitool and Router, then Hooks).

## Today (read in the code)
- `Session/ToolCallHooks.swift`: `run` (line ~87) sends PreToolUse (`admit`), runs the body, then `screenResult` sends PreToolResult and then `post(_:output:succeeded:)` (line ~186).
- `succeeded` is `false` in three places: PreToolUse refusal (`.refused`, line ~99), a body that throws (line ~108), a PreToolResult block (line ~172). It is `true` otherwise (line ~175). A nonzero shell exit returns normally, so the hook sees `true`.
- The only `ToolCallWitness` conformer in the Router is `AgentDelegationAdvisor`; `ToolCallWitness` has no public way to read the final result of a call after the body returns.

## Goal
`PostToolUse` (FoundationModelsHooks, HookEvents.swift:242) loses `succeeded` and gets `result: OperationResult` (Hooks card 01M6HA6GAC7K7A3TH6RJV94TAF). Proposed names, from Extras (task 01M6HA3B670G61TZ115SGX9DAA, not started, NOT final): `OperationResult` (outcome: OperationOutcome, value: OperationValue?) and `OperationValue` (int, string, bool, object). Extras also proposes `toolCallDidEnd(_ call: WitnessedToolCall, result: OperationResult)` on `ToolCallWitness`. Multitool will call `ToolContext.current?.reportFailure(value: .int(exitCode))` on a nonzero shell exit (task 01M6HA2RQ7K35W788Y20JNRBPA).

## Plan (Router side)
1. Wait for Extras to publish `OperationResult` and the witness call. Do not invent a local copy of the type.
2. In `ToolCallHooks.run`, after the body returns, read the final result of the call through the witness call (`toolCallDidEnd`): it carries the outcome and value that the tool reported (for example a shell tool reports failed with `.int(exitCode)`). If the tool reported nothing, the result is `succeeded` with no value.
3. Build the `PostToolUse` result:
   - body returned, no report: `OperationResult(outcome: .succeeded, value: nil)`;
   - tool reported a result: that result;
   - body threw: `failed` (a `CancellationError` gives `cancelled`; a timeout gives `timedOut`; a `LostRunError` gives `lost`), value is the error text;
   - PreToolUse refusal: `failed` with the reason as the value;
   - PreToolResult block: `failed` with the reason as the value (the model still gets the reason).
4. Change `post(_:output:succeeded:)` to `post(_:output:result:)`. No Bool and no shim: remove `succeeded` from every call and from the docs and the tests.
5. Check the other readers of the hook event in the Router (tests under `Tests/FoundationModelsRouterTests` that assert `succeeded`, docs in `FoundationModelsRouter.docc`) and update them.

## Open points for the user and Extras

- Whether the value of a thrown error is the error text or `nil`.
- A call that a suspended session (suspend()) drops: no PostToolUse change is planned.
