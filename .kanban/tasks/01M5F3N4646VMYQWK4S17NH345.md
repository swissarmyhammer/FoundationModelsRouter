## Goal
`SessionDirectory.send` delivers a message to each resolved target as a `Mail`, keeps a `SessionMessage` record (sender, `inReplyTo`, chain depth, client id of a UI sender, read flag), sends `messageDelivered`, and `inbox(of:markRead:)` gives the unread messages.

## Blocked on a spec decision (tag needs-decision)
1. **Spec conflict, the mail body of a UI message.** FoundationModelsMultitool/session.md section 6 (notes) says a UI message goes as `Mail(sender: .user, body: .agentMessage…)`; section 10.1 (last paragraph) says a UI message renders as a user message, not as an agent message. Also `MailBody.agentMessage(from:)` needs a session ULID that a user does not have. The plan below uses `.userMessage`; the spec owner must choose.
2. **Where the message record lives.** `Mail` has no field for `inReplyTo`, chain depth or the UI client id. The plan keeps them in a Router ledger file `messages.jsonl` in the target's recording directory; the spec owner must accept that name and place (or ask Extras for a `Mail` field instead).
Remove the tag and this section when both are answered.

## What
- New `/Users/wballard/github/swissarmyhammer/FoundationModelsRouter/Sources/FoundationModelsRouter/Directory/SessionMessageLedger.swift`: the record of the messages to each session, keyed by `MailID`: `SessionMessage` plus the UI client id. `Mail` (Extras `Mail/Mail.swift`) has only `id`, `sender` and `body`, and `MailSender.user` has no client id, so the ledger, not the mail, keeps `inReplyTo`, `chainDepth` and the client id. Persist it as an append-only `messages.jsonl` in the target's recording directory (Router's `Recording/JSONLAppend.swift`), with a later line for each read mark, so the inbox survives a restore. This file name and place need a yes from the spec owner (see the plan questions).
- `/Users/wballard/github/swissarmyhammer/FoundationModelsRouter/Sources/FoundationModelsRouter/Directory/RouterSessionDirectory.swift`, replace the provisional `send` and `inbox`:
  - Resolve with the address resolver (ROUTER-4 resolver card). For each live target: `Mail(sender: .session(from), body: .agentMessage(from: from, content: text))` through `MailSink.mail(_:)` (`Session/RoutedSessionActorQueueing.swift`); the existing `MailRecord.mailQueued` record (`Session/RoutedSessionActorMailRecords.swift`) already keeps the sender in the transcript. A UI sender (`.user(clientID:)`) has no session id for `.agentMessage(from:)`: plan `Mail(sender: .user, body: .userMessage(...))`, because section 10.1 shows a UI message as a user message (confirm with the spec owner).
  - `startAgent`: `start(SessionStartRequest(agentID:, workingDirectory: folder, firstMessage: text, startedBy: from session, origin: .message))` through the launcher (ROUTER-8); receipt `started` with the new id. No launcher throws `noLauncher`.
  - `refused` decisions give a `refused` receipt with the reason. `restoreThenDeliver` gives `refused` with "not live" until ROUTER-5.
  - Receipt `delivered` for each live target in this card (ROUTER-5 adds `queued`). Chain depth is 1 here (ROUTER-5 computes it).
  - After each delivery, `messageDelivered(SessionMessage)`.
  - `inbox(of:markRead:)`: the unread messages to `id`, oldest first; with `markRead`, mark them read in the ledger.
