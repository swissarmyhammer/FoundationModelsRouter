## What
No timer and no race decide behavior. The default for every tool is run-to-completion; a tool that is known ahead of time to run long declares background about itself. One knob remains: `timeout`. Work in `Sources/FoundationModelsRouter/Hosting/DetachingTool.swift` plus the one real composition site.

- [ ] Delete `DetachConfiguration.waitSeconds`, `defaultWaitSeconds`, the `waitSeconds:` init parameter, `clockRelationFailure(tool:mode:waitSeconds:timeout:)`, and `DetachingToolError.invalidClocks(tool:waitSeconds:timeout:)`.
- [ ] Rename `Mode.detaching` to `Mode.background`. Keep `Mode.runToCompletion`.
- [ ] The declaration API is exact: a long-running tool declares
      `var detachmentMount: DetachConfiguration? { DetachConfiguration(mode: .background, timeout: nil) }`
      (or a long timeout). No new member for the mode. A tool that declares nothing is synchronous.
- [ ] Replace `DetachmentParameterProviding.detachmentClocks(from:) -> (waitSeconds: TimeInterval?, timeout: TimeInterval?)` (public, 6 conformers) with a timeout-only member: `detachmentTimeout(from:) -> TimeInterval?`. Keep the blanket default. The per-call `timeout` path MUST stay alive — `../FoundationModelsMultitool/Sources/FoundationModelsMultitool/MultiTool+Detachment.swift:98` bounds every `runCode` call with it.
- [ ] The one composition site is `ToolDetachment.sessionMounted` in `Sources/FoundationModelsRouter/Session/ToolOutputCapping.swift:189-204` (all of `RoutedModel.makeSession`, `RoutedSessionActor.fork`, and `restoreSessionTree` go through it). Flip it: `nativeSessionMount` becomes exactly `DetachConfiguration(mode: .runToCompletion, timeout: defaultTimeoutSeconds)` (120 s — a synchronous tool that hangs reports `timedOut`); a tool's own `.background` declaration wins. Rewrite that site's doc comment (lines 145-177) — it narrates the old mount policy.
- [ ] Doc comments state the examples: shell and agent tools declare background; file edit, skill, and discovery tools do not.
