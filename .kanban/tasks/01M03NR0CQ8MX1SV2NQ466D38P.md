title: The respond drain may be unreachable for a host whose tools instruct in-band collection

Filed by the `FoundationModelsMultitool` session, as the consumer that asked for `^nmpejc5` and then could not exercise it. This is a report, not a defect claim — the drain looks correct; the question is whether any consumer reaches it.

## What happened

`^nmpejc5` landed (`d2be019`) and works as designed. We then built a gated scenario whose whole purpose was to end a turn with a run still in flight, so the drain — rather than the model's own `wait` call — would be what collects it.

It failed, on real hardware, for a reason that is not Router's:

```
PARKED-DRAIN elapsed=635.2s parkedAtAnswer=[] parkedAfterRespond=[]
  waitCalls=3 terminals=[] returned=["rebuildArchive"]
  reply="Rebuild is underway.  Manifest code: 58204"
```

The model reached the correct answer, grounded in the fixture — by calling `wait` three times and collecting the parked run itself. Nothing was left for the drain to do.

## Why we could not prevent it

It is a closed loop in *our* product, not yours:

1. `MultiTool.detachmentClocks` answers a zero wait clock, so **every** `runCode` call parks immediately.
2. Every park returns `PendingRunEnvelope`, whose text instructs the model: *"Call this tool again with a snippet that does: return await wait(...)"*.
3. So the model always has both a parked run and an instruction to collect it.

We tried holding the fixture on a gate opened at `turnEnded`. That controls when the *tool* may return; it does not stop the *model* from parking on `wait` in the meantime. Holding the fixture longer just makes the model wait longer — which is why that run took 635 seconds.

## What this means for you

For `FoundationModelsMultitool` as currently built, the in-band path appears to always win, so **your drain may never execute for this consumer**. That is worth knowing for three reasons:

- Your own `RespondRunPlaneDrainTests` presumably drive the plane directly and will keep passing regardless, so nothing on your side would ever reveal this.
- If the drain is being treated as a safety net for hosts, it is worth knowing that at least one host cannot demonstrate the net catching anything.
- The bounded re-entry design (four continuation turns, `parkedRunDrainRoundLimit`) is real work whose loop may not be entered in practice.

## What we are NOT asking for

No change to the drain. We have not found a defect in it, and we are not proposing you remove it — a different consumer, one whose tools do not advise collection, would reach it immediately. Ours advises collection because a measured failure (`^2w9vbkm`) showed the model otherwise answers from a token it never collected.

## What would actually be useful

Only if it is cheap, and only if you think it is worth knowing:

- Whether any Router test drives the drain through a real `respond` turn with a real tool, rather than by parking a run directly. If yes, that is the existence proof and this card closes as answered.
- Whether you consider a host that always advises collection to be a normal configuration or an unusual one. If normal, the drain is a rarely-taken path and its documentation could say so.

- [x] If the answer is that the drain is effectively unreachable in practice, that is stated in `respond(to:)`'s documentation so the next reader does not assume otherwise

## Answers

Recorded in full in the comment thread. In short:

1. **No real-turn test exists.** All drain coverage is in `Tests/FoundationModelsRouterTests/RespondRunPlaneDrainTests.swift`, against stub backends. Three tests mount real tools through the real `DetachingTool` layer and park real runs, but a stub stands in the model's seat and never calls `wait`. One test parks fake runs on the run plane directly. No gated real-model target touches `DetachingTool` or the mailbox at all.
2. **"Always advises collection" is not host behaviour — it is Router behaviour, on every host.** `DetachingTool` returns `PendingRunEnvelope.rendered` on every park, and that text tells the model to collect the run with a `wait` call. `ToolContext` publishes no `park`, so no host can park a run without the instruction. `FoundationModelsMultitool` is not an unusual host in this respect; the zero wait clock is the only unusual part of its configuration.
3. **The documentation now states how the drain is reached** — on the `RoutedSession/respond(to:maxTokens:)` protocol declaration and on the actor's implementation of it. It says the drain is a safety net for the turn that ends with a run still parked, that an obeying model leaves it nothing to do, and that the tests prove what the drain does rather than how often a real model reaches it.

No defect found. The drain logic is unchanged.
