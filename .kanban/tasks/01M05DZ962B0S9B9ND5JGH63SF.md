    Four changes, all in `Sources/FoundationModelsRouter`.

    **1. The run-to-completion mount.** `DetachConfiguration.timeout` is now `TimeInterval?`, where `nil` means no clock at all, and `DetachConfiguration.runToCompletionMount` is the pair a host asks for the mode by: `.runToCompletion` with `timeout: nil`. `raceInnerAgainstTimeout` starts no watcher for a `nil` timeout, so nothing but the wrapped tool's own failure can reach the model. This is not a long timeout, and the mount's own doc says why a long timeout is not a substitute.

    **2. The clock relation is rejected.** `DetachConfiguration.clockRelationFailure(tool:mode:waitSeconds:timeout:)` is the one implementation of the rule: in `.detaching`, with a stated timeout, `waitSeconds` must stand strictly under `timeout`. `DetachingTool.call` applies it to the clocks the call actually resolved to — the wrap-time configuration merged with a `DetachmentParameterProviding` override — and throws `DetachingToolError.invalidClocks` before any work starts, so a refused call leaves no run, no parked token and no event.     The consumer is right, and the gap is closed with shape 1: **a tool declares its mount the way it declares its clocks.**


    `DetachingTool.init` resolves it once: `(wrapped as? any DetachmentParameterProviding)?.detachmentMount ?? configuration`. A tool that declares nothing keeps the configuration its composition site passed, so nothing that works today changes.

    **Why the whole mount, and not only `mode`.** The card offered `mode`, but a mode alone cannot say what the consumer needs. In `.runToCompletion` the wrap-time `timeout` still bounds the work, and a `nil` clock in `detachmentClocks(from:)` means "fall back", never "no clock". So a tool that declared only its mode while mounted on `.nativeSessionMount` would still carry the 120 second timeout — a slow search reported as a failed search, which is the thing they refuse. `DetachConfiguration.runToCompletionMount` states mode and no-clock together, and that is exactly the name a tool now writes.

title: Give a tool a run-to-completion mode, and validate waitSeconds against timeout
---
A host cannot say "this tool blocks until it is done and never parks". A host that tries to say it with the clocks we give gets behaviour we do not intend.

## The host requirement

The `FoundationModelsMultitool` session has a discovery tool. A model cannot write a snippet until it knows which paths exist, so discovery is a synchronous prerequisite. If discovery parks, the model gets a pending envelope for a call it must go and collect. They measured that result and it was bad: every discovery call parked, the model never got the catalogue, and three runs ended with no tool calls and an answer that said it had no access.

So they need the tool to block. They ask for it with `waitSeconds = timeout = 86_400`.

## What those values do

`waitSeconds >= timeout` is not implemented as "never detach". Nothing implements that reading.

- Both clocks clamp through `SessionMailbox.boundedNanoseconds(clamping:)` with the same `ToolContext.waitSecondsCeiling` (`Hosting/DetachingTool.swift:420-427` and `:580-587`). The name is wrong at the second site.
- `DetachConfiguration.init` (`:100-108`) and the per-call override (`:358-360`) store both clocks with no validation and no relational check.
- The two clocks are independent timers started at the same time. They never consult each other.

So with 86400 and 86400 the call blocks in band for a full day, and then the clocks race. `waitSeconds` arms with fewer scheduling hops, so it usually wins: the call detaches, and the timeout watcher then stops the run it just parked (`:565-570`). The model gets a pending token for a dead run. If the race goes the other way, `call` throws `DetachingToolError.timedOut` in band. Which one you get is timing.

Our stock design assumes the opposite relation. `DetachingTool.swift:61-65` says the 120 second timeout is "deliberately much longer than" the 5 second wait "so at stock settings the soft deadline always wins". The host inverted that, and no code defends the inversion.

## Missing tests

`Tests/FoundationModelsRouterTests/SessionMailboxTests.swift:66-83` covers only the low end of the clamp: `-1.0`, `0.0`, `NaN`. No test refers to `waitSecondsCeiling`. No test uses `waitSeconds == timeout` or `waitSeconds > timeout`.

## Acceptance Criteria

- [x] A host can ask for run-to-completion directly, and the request is clear in the API
- [x] In that mode the tool never parks, and only a real error reaches the model
- [x] `waitSeconds >= timeout` is rejected, or it is given a defined and documented behaviour
- [x] The race between the two clocks cannot give the model a token for a run that is already dead
- [x] Tests cover `waitSeconds == timeout`, `waitSeconds > timeout`, and the ceiling
- [x] The misleading use of `waitSecondsCeiling` as the timeout ceiling is corrected or renamed
