title: Give a tool a run-to-completion mode, and validate waitSeconds against timeout
---
A host cannot say "this tool blocks until it is done and never parks". A host that tries to say it with the clocks we give gets behaviour we do not intend.

## The host requirement

The `FoundationModelsMultitool` session has a discovery tool. A model cannot write a snippet until it knows which paths exist, so discovery is a synchronous prerequisite. If discovery parks, the model gets a pending envelope for a call it must go and collect. They measured that result and it was bad: every discovery call parked, the model never got the catalogue, and three runs ended with no tool calls and an answer that said it had no access.

So they need the tool to block. They ask for it with `waitSeconds = timeout = 86_400`.

## What those values do

`waitSeconds >= timeout` is not implemented as "never detach". Nothing implements that reading.

- Both clocks clamp through `SessionMailbox.boundedNanoseconds(clamping:)` with the same `ToolContext.waitSecondsCeiling` (`Hosting/DetachingTool.swift:420-427` and `:580-587`). The name is wrong at the second site.
- `DetachConfiguration.init` (`:100-108`) and the per-call override (`:358-360`) store both clocks with no validation and no relational check.
- The two clocks are independent timers started at the same time. They never consult each other.

So with 86400 and 86400 the call blocks in band for a full day, and then the clocks race. `waitSeconds` arms with fewer scheduling hops, so it usually wins: the call detaches, and the timeout watcher then stops the run it just parked (`:565-570`). The model gets a pending token for a dead run. If the race goes the other way, `call` throws `DetachingToolError.timedOut` in band. Which one you get is timing.

Our stock design assumes the opposite relation. `DetachingTool.swift:61-65` says the 120 second timeout is "deliberately much longer than" the 5 second wait "so at stock settings the soft deadline always wins". The host inverted that, and no code defends the inversion.

## Missing tests

`Tests/FoundationModelsRouterTests/SessionMailboxTests.swift:66-83` covers only the low end of the clamp: `-1.0`, `0.0`, `NaN`. No test refers to `waitSecondsCeiling`. No test uses `waitSeconds == timeout` or `waitSeconds > timeout`.

## Acceptance Criteria

- [ ] A host can ask for run-to-completion directly, and the request is clear in the API
- [ ] In that mode the tool never parks, and only a real error reaches the model
- [ ] `waitSeconds >= timeout` is rejected, or it is given a defined and documented behaviour
- [ ] The race between the two clocks cannot give the model a token for a run that is already dead
- [ ] Tests cover `waitSeconds == timeout`, `waitSeconds > timeout`, and the ceiling
- [ ] The misleading use of `waitSecondsCeiling` as the timeout ceiling is corrected or renamed
