## What

`Sources/FoundationModelsRouter/Hosting/RunPlane.swift` says it in its own doc
comment: *"Phase 1 ships `swiftTask` only; this enum is
the seam where the `process` (phase 2) and `mcpRequest` (phase 4) kinds land."*

Phase 2 of eventplan.md moves the shell capability into MultiTool. A shell run
is an OS process group, not a Swift task. eventplan.md § "Consolidation of the
siblings" fixes the distinction:

> An OS process group (shell). `killpg(SIGKILL)` is authoritative. The outcome
> is `.stopped`.

A shell run that parks as `RunKind.swiftTask` reports the wrong cancellation
authority. `OperationOutcome` makes that distinction mandatory.

- Edit `Sources/FoundationModelsRouter/Hosting/RunPlane.swift`:
  - Add `case process` to `RunKind`.
  - Give it a doc comment that states the authority: `killpg(SIGKILL)` is
    authoritative, so a canceler for this kind reports
    `OperationOutcome.stopped`, never `.cancelled`.
- Check `Sources/FoundationModelsRouter/Hosting/SessionMailbox.swift`. The
  `sweep()` function must process a `process` run with that run's own canceler.
  The canceler comes from the capability. Router does not know about `killpg`.
- Router owns no shell code. This task adds the vocabulary only.

The requester is the FoundationModelsMultitool board, task `wjdyxz3` ("Port
ShellRunner as a run body and a canceler"). That task is blocked until this
lands.
